Phase 1

DevOps & CI/CD Foundations

DevOps Kya Hota Hai? (The Big Picture)

Bhai, socho ek restaurant hai. Kitchen team (Developers) log khaana banate hain aur Waiter team (Operations) log customers ko serve karti hai. Purane zamaane mein dono teams ek doosre se baat nahi karti thi – kitchen wale bolte "humara kaam hua, hamare haath se gaya" aur waiters bolte "yeh toh theek se ready hi nahi hai!"

DevOps ne kaha – dono teams ko saath milkar kaam karna chahiye. Ek shared responsibility, ek shared goal: software jaldi aur reliably deliver karo.

🚗 Real-Life Analogy – Assembly Line of Cars

DevOps waise hi hai jaise modern car factory ki assembly line. Har stage automated hai – welding robot, paint machine, quality check sensor – aur agar ek jagah problem aati hai toh poori line ruk jaati hai. Koi bhi "manually" gap nahi bharta. Yahi concept software delivery mein apply hota hai DevOps se.

DevOps = Culture + Process + Tools

  • Culture: Dev aur Ops ek team hain, blame game nahi
  • Process: Automation first, manual steps minimize karo
  • Tools: Jenkins, Docker, Kubernetes, Terraform, etc.
💡
Why Companies Care? Amazon ek time pe hafte mein sirf 1 release karta tha. DevOps adopt karne ke baad ab wo har second mein multiple deployments karta hai. Speed = competitive advantage = more money.

CI/CD Kya Hota Hai?

CI/CD do concepts hain – Continuous Integration aur Continuous Delivery/Deployment. Dono milke ek pipeline banate hain jo code ko developer ke laptop se production server tak automatically le jaati hai.

🔵 Continuous Integration (CI) – Continuous Jodna

Jab bhi koi developer code likhke GitHub pe push karta hai, automatically yeh kaam hota hai:

  • Code build hota hai (compile ya package)
  • Unit tests run hote hain
  • Code quality check hoti hai (linting)
  • Security vulnerabilities scan hoti hain

🟢 Continuous Delivery (CD) – Continuous Pahunchana

CI ke baad code automatically staging environment mein deploy hota hai. Production mein jaane ke liye ek manual approval ki zaroorat hoti hai. Yeh "Delivery" hai.

🚀 Continuous Deployment – Poora Automatic

Yahan koi manual step nahi. Agar sab tests pass ho gaye toh code automatically production mein chala jaata hai. Netflix aur Google yehi karte hain.

Jenkins Architecture Deep Dive

Jenkins Ki Duniya – Controller & Agent Architecture

Jenkins ek distributed system hai. Iske do main components hain:

  • Jenkins Controller (Master): Yeh boss hai. Yeh decide karta hai kaunsa job kab chalega, logs store karta hai, UI serve karta hai, aur agents ko instructions deta hai. Build khud nahi chalaata.
  • Jenkins Agent (Node/Slave): Yeh worker hai. Actual build commands yahan chalte hain. Multiple agents ho sakte hain – different OS, different tools, alag-alag capability ke saath.

🏢 Analogy – Project Manager aur Team Members

Controller ek Project Manager ki tarah hai jo tasks assign karta hai aur status track karta hai. Agents developer/tester team ki tarah hain jo actual kaam karte hain. PM khud coding nahi karta – sirf manage karta hai. Exactly yehi Jenkins mein hota hai.

Controller pe Build Kyun Nahi Chalate?

Yeh ek critical production rule hai! Controller pe build chalane se:

  • Controller ki CPU/RAM consume hoti hai → UI slow ho jaata hai
  • Security risk – build scripts controller ke OS pe direct access paa leti hain
  • Scaling impossible ho jaati hai
🚨
Production Rule: Jenkins controller pe agent none configure karo aur har pipeline mein explicitly agent specify karo. Controller pe built-in executor ko 0 set karo!

Jenkins Ke Andar Kya Hota Hai? (Internals)

1. Job Queue (Build Queue)

Jab tumhare paas zyaada builds aate hain aur agents busy hain, Jenkins unhe queue mein daal deta hai. Yeh ek waiting line hai. Queue configuration aur priority management production mein bahut important hai.

2. Build Executor

Har agent pe ek ya zyaada executors hote hain – yeh woh "slots" hain jahan builds chalte hain. 2 executors = 2 parallel builds on same agent.

3. Plugin System

Jenkins ki real power iske 1800+ plugins hain. Plugins Jenkins ko extend karte hain – naye build steps, naye SCM systems, naye notification channels, sab kuch plugins se aata hai.

Jenkins Home Directory (JENKINS_HOME)

Jenkins ka saara data ek folder mein hota hai – JENKINS_HOME (default: /var/lib/jenkins on Ubuntu).

JENKINS_HOME Structure

├── config.xml          # Main Jenkins configuration

│   ├── my-app/
│   │   ├── config.xml  # Job config
│   │   └── builds/     # Build history, logs, artifacts

Backup Strategy: Production mein JENKINS_HOME ka regular backup lo! Especially config.xml aur jobs/ folder. Agar yeh chale gaye toh saara setup dubara karna padega. AWS S3 ya Google Cloud Storage pe backup rakho.

💼 Interview Questions – Phase 2

Q: Jenkins Master pe build chalana kyun risky hai? Controller pe build chalane se resource contention hoti hai (UI slow padti hai), security risk hota hai (build scripts OS access paa leti hain), aur horizontal scaling impossible ho jaati hai. Best practice: controller pe executor count = 0.
Q: Jenkins agent ko controller se kaise connect karte hain? Do main methods: (1) SSH – controller agent pe SSH karta hai aur Java process start karta hai. (2) JNLP/TCP – agent controller se connection initiate karta hai port 50000 pe. Firewall ke peeche wale agents ke liye JNLP better hota hai.
Q: Jenkins failover kaise handle karte hain? Active-passive setup: primary Jenkins controller ka JENKINS_HOME shared storage (NFS/EBS) pe rakho. Secondary controller same storage mount kare. Primary fail ho toh secondary manually/automatically start karo. Modern approach: Jenkins on Kubernetes with persistent volume.

Post-Installation – Production Settings

BASH – Production Hardening (Jenkins Service Config)

[Service]

Production Setup – Nginx Reverse Proxy + HTTPS

Production mein Jenkins ko directly port 8080 pe expose mat karo. Nginx reverse proxy use karo SSL ke saath.

BASH – Nginx + Certbot Setup 
# Nginx install karo
sudo apt install nginx -y

# Certbot install karo (free SSL)
sudo apt install certbot python3-certbot-nginx -y

# SSL certificate banao (apna domain use karo)
sudo certbot --nginx -d jenkins.yourcompany.com

# Nginx config create karo
sudo nano /etc/nginx/sites-available/jenkins
NGINX CONFIG – Jenkins Reverse Proxy with SSL 
upstream jenkins {
  keepalive 32;
  server 127.0.0.1:8080 fail_timeout=0;
}

server {
  listen 80;
  server_name jenkins.yourcompany.com;
  return 301 https://$server_name$request_uri;
}

server {
  listen 443 ssl http2;
  server_name jenkins.yourcompany.com;

  ssl_certificate     /etc/letsencrypt/live/jenkins.yourcompany.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/jenkins.yourcompany.com/privkey.pem;

  # Security headers
  add_header X-Frame-Options            SAMEORIGIN;
  add_header X-XSS-Protection           "1; mode=block";
  add_header X-Content-Type-Options     nosniff;
  add_header Strict-Transport-Security  "max-age=63072000; includeSubDomains";

  ignore_invalid_headers off;

  location / {
    proxy_pass         http://jenkins;
    proxy_http_version 1.1;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
    proxy_connect_timeout 150;
    proxy_send_timeout    100;
    proxy_read_timeout    100;
    proxy_buffers         4 32k;
    client_max_body_size  8m;
    client_body_buffer_size 128k;
  }
}

💼 Interview Questions – Phase 3

Q: Jenkins ko Docker mein run karne ke advantages aur disadvantages? Advantages: Fast setup, portable, easy to update, version pinning. Disadvantages: Docker-in-Docker complexity (builds ke liye Docker access chahiye), persistent storage manage karna padta hai, container networking tricky ho sakti hai agents ke saath.
Q: Jenkins ka port 8080 directly expose kyun nahi karte production mein? Security reasons: Jenkins directly internet pe accessible hona risky hai – brute force attacks, vulnerability exploits. Nginx reverse proxy: SSL termination, security headers, rate limiting, access control sab ek jagah milta hai.
Q: JENKINS_HOME backup strategy batao? 3-2-1 rule follow karo: 3 copies, 2 different media, 1 offsite. Daily automated backup to S3/GCS, weekly full backup, monthly archived backup. Thin Backup Plugin ya simple rsync + cron. Configuration as Code (JCasC) better approach – config YAML files Git mein rakho.

Jobs, Pipelines & Jenkinsfile

Jenkinsfile – Jenkins Ka Heart

Jenkinsfile ek text file hai jo tumhari pipeline ko define karta hai. Yeh file tumhare code ke saath repository mein hoti hai – yeh concept kahlata hai "Pipeline as Code".

📋 Analogy – Recipe Card

Jenkinsfile bilkul ek recipe card ki tarah hai. Jaise recipe mein likha hota hai "Step 1: Pyaaz kaato, Step 2: Tel daalo, Step 3: Fry karo" – waise hi Jenkinsfile mein likha hota hai "Stage 1: Code nikalo, Stage 2: Build karo, Stage 3: Test karo". Koi bhi yeh recipe le ke same dish bana sakta hai – koi bhi Jenkins server yeh Jenkinsfile le ke same pipeline run kar sakta hai.

Declarative Pipeline Structure

JENKINSFILE – Complete Structure with All Options 
// Declarative Pipeline – Yeh structure yaad rakho!
pipeline {
  // 1. AGENT – Kahan chalana hai?
  agent {
    label 'linux-docker'    // specific agent
    // ya: any  – koi bhi available agent
    // ya: none – individual stage pe define karo
  }

  // 2. ENVIRONMENT – Environment variables
  environment {

💼 Interview Questions – Phase 5

Q: Webhook aur Poll SCM mein kaun better hai aur kyun? Webhook better hai: (1) Instant trigger – no delay (2) Less load – Jenkins constantly check nahi karta (3) Exact event-based – sirf push pe trigger. Poll SCM: fallback when webhooks not possible (corporate firewall, private network). Best practice: dono use karo – webhook primary, pollSCM fallback.

Q: PR pe deploy karna chahiye ya nahi? Depends on team size. Small teams: PR pe staging deploy karo for review. Large teams: PR pe sirf build + test, merge ke baad deploy. Feature flags se PRs bina deploy ke test kar sakte hain production mein. Most companies: merge ke baad staging pe auto-deploy, production manually.

        script {
          // Build karo
          docker.build("${IMAGE_NAME}:${IMAGE_TAG_FULL}", """
            --build-arg BUILD_DATE=\$(date -u +'%Y-%m-%dT%H:%M:%SZ') \
            --build-arg GIT_COMMIT=${env.GIT_COMMIT_SHORT} \
            --build-arg VERSION=${IMAGE_TAG_FULL} \
            --label git-commit=${env.GIT_COMMIT_SHORT} \
            --label build-number=${IMAGE_TAG} \
            .
          """)

          // Image scan karo security ke liye (Trivy)
          sh """
            trivy image \
              --exit-code 1 \
              --severity HIGH,CRITICAL \
              --no-progress \
              ${IMAGE_NAME}:${IMAGE_TAG_FULL}
          """
        }
      }
    }

    stage('Push to Registry') {
      steps {
        script {
          docker.withRegistry("https://${REGISTRY}", 'docker-hub-creds') {
            def img = docker.image("${IMAGE_NAME}:${IMAGE_TAG_FULL}")
            img.push()                            // Push with build+commit tag
            img.push('latest')                    // Push latest tag too

            if (env.BRANCH_NAME == 'main') {
              img.push('stable')                  // main branch = stable
            }
          }
        }
      }
    }

    stage('Deploy to Staging') {
      when { branch 'develop' }
      steps {
        sh """
          ssh -o StrictHostKeyChecking=no deploy@staging.company.com '
            docker compose -f /opt/apps/docker-compose.yml pull
            docker compose -f /opt/apps/docker-compose.yml up -d --no-build
            docker compose -f /opt/apps/docker-compose.yml ps
          '
        """
      }
    }

    stage('Smoke Test') {
      when { branch 'develop' }
      steps {
        sh """
          sleep 30  # Container warm-up time
          curl -f https://staging.company.com/actuator/health | \
            python3 -c "import sys,json; d=json.load(sys.stdin); sys.exit(0 if d['status']=='UP' else 1)"
          echo "Smoke test passed!"
        """
      }
    }

    stage('Deploy Production') {
      when { branch 'main' }
      steps {
        timeout(time: 1, unit: 'HOURS') {
          input message: "Production deploy approved?",
                submitter: 'tech-lead,devops-team'
        }
        // Blue-Green Deployment
        sh """
          ssh deploy@prod.company.com '
            CURRENT_COLOR=\$(docker inspect --format="{{ .Name }}" app-blue 2>/dev/null | grep -c blue || echo "0")
            
            if [ "\$CURRENT_COLOR" = "1" ]; then
              NEW_COLOR="green"; OLD_COLOR="blue"
            else
              NEW_COLOR="blue";  OLD_COLOR="green"
            fi
            
            echo "Deploying to \$NEW_COLOR..."
            docker run -d \
              --name "app-\$NEW_COLOR" \
              -p 8081:8080 \
              --restart unless-stopped \
              ${IMAGE_NAME}:${IMAGE_TAG_FULL}
            
            sleep 30
            curl -f http://localhost:8081/actuator/health
            
            echo "Switching traffic to \$NEW_COLOR..."
            nginx-switch-upstream.sh \$NEW_COLOR
            
            sleep 10
            docker stop "app-\$OLD_COLOR" || true
            docker rm "app-\$OLD_COLOR"   || true
            
            echo "Blue-Green deployment complete!"
          '
        """
      }
    }
  }

  post {
    always {
      sh "docker rmi ${IMAGE_NAME}:${IMAGE_TAG_FULL} || true"
      cleanWs()
    }
    success {
      slackSend color: 'good',
                message: "✅ Deployed ${IMAGE_NAME}:${IMAGE_TAG_FULL} successfully!"
    }
    failure {
      slackSend color: 'danger',
                message: "❌ Deployment FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER}"
    }
  }
}

💼 Interview Questions – Phase 6

Q: Multi-stage Docker build kyun use karte hain? Final image chota hota hai (only runtime dependencies, not build tools). Builder stage mein Maven 300MB, final runtime image mein sirf JRE = much smaller. Smaller image = faster pulls, less attack surface, less storage cost. Practical example: Spring Boot app – builder 800MB, final image 150MB.
Q: Blue-Green deployment kya hai? Do identical production environments: Blue (current live) aur Green (new version). Deploy to Green, test karo, phir traffic switch karo Blue se Green pe. Agar koi issue hai toh instantly Blue pe wapas switch karo. Zero downtime deployment + instant rollback capability.
Q: Docker image security best practices kya hain? (1) Non-root user use karo (2) Specific base image version pin karo (3) Multi-stage build se attack surface kam karo (4) Trivy/Snyk se vulnerability scan karo (5) .dockerignore file use karo (6) Secrets kabhi image mein mat daalte – env vars ya secrets manager use karo.

/**
 * Docker image build aur push karne ka reusable function
 * Usage: buildDockerImage(imageName: 'myapp', registry: 'docker.io/myco')
 */
def call(Map config = [:]) {
  // Default values with overrides
  def imageName  = config.imageName  ?: error("imageName required!")
  def registry   = config.registry   ?: 'registry.hub.docker.com'
  def credId     = config.credId     ?: 'docker-hub-creds'
  def dockerfile = config.dockerfile ?: 'Dockerfile'
  def buildArgs  = config.buildArgs  ?: [:]
  def tags       = config.tags       ?: ['latest', env.BUILD_NUMBER]

  def fullImageName = "${registry}/${imageName}"

  pipeline.stage("Docker Build: ${imageName}") {
    script {
      // Build args string banana
      def buildArgsStr = buildArgs.collect { k, v ->
        "--build-arg ${k}=${v}"
      }.join(' ')

      def buildTag = "${fullImageName}:${env.BUILD_NUMBER}"

      sh """
        docker build \
          -f ${dockerfile} \
          ${buildArgsStr} \
          -t ${buildTag} \
          --label git-commit=${env.GIT_COMMIT} \
          --label build-date=\$(date -u +'%Y-%m-%dT%H:%M:%SZ') \
          .
      """

      docker.withRegistry("https://${registry}", credId) {
        def img = docker.image(buildTag)
        tags.each { tag ->
          img.push(tag)
          echo "Pushed: ${fullImageName}:${tag}"
        }
      }

      env.DOCKER_IMAGE_FULL = "${fullImageName}:${env.BUILD_NUMBER}"
    }
  }
}

@Library('company-jenkins-library@v3.0.0') _

pipeline {
  agent { label 'k8s-build-agent' }

  environment {
    SERVICE_NAME   = 'order-service'
    DOCKER_REGISTRY= 'your-account.dkr.ecr.ap-south-1.amazonaws.com'
    DOCKER_IMAGE   = "${DOCKER_REGISTRY}/${SERVICE_NAME}"
    K8S_NAMESPACE  = 'ecommerce'
    SONAR_PROJECT  = "ecommerce-${SERVICE_NAME}"
    AWS_REGION     = 'ap-south-1'
    JIRA_PROJECT   = 'EC'
  }

  options {
    timestamps()
    ansiColor('xterm')
    buildDiscarder(logRotator(numToKeepStr: '15', artifactNumToKeepStr: '5'))
    timeout(time: 60, unit: 'MINUTES')
    disableConcurrentBuilds(abortPrevious: true)
  }

  parameters {
    booleanParam(name: 'FORCE_DEPLOY_PROD', defaultValue: false,
                 description: 'Force production deploy without tests?')
    string(name: 'IMAGE_TAG_OVERRIDE', defaultValue: '',
           description: 'Override image tag (for rollback)')
  }

  stages {
    stage('🔍 Checkout & Setup') {
      steps {
        checkout scm
        script {
          env.GIT_COMMIT_SHORT = sh(script: 'git rev-parse --short HEAD', returnStdout: true).trim()
          env.IMAGE_TAG = params.IMAGE_TAG_OVERRIDE ?: "${env.BUILD_NUMBER}-${env.GIT_COMMIT_SHORT}"
          env.FULL_IMAGE = "${DOCKER_IMAGE}:${env.IMAGE_TAG}"
          env.IS_RELEASE = (env.BRANCH_NAME =~ /^main$/).asBoolean()

          sh """
            echo "Service:    ${SERVICE_NAME}"
            echo "Branch:     ${env.BRANCH_NAME}"
            echo "Commit:     ${env.GIT_COMMIT_SHORT}"
            echo "Image:      ${env.FULL_IMAGE}"
            echo "Is Release: ${env.IS_RELEASE}"
          """
        }
      }
    }

    stage('🔨 Build') {
      steps {
        sh '''
          mvn clean package \
            -DskipTests=true \
            -Dmaven.compiler.source=21 \
            -Dmaven.compiler.target=21 \
            --batch-mode \
            --no-transfer-progress
        '''
        archiveArtifacts artifacts: 'target/*.jar', fingerprint: true
      }
    }

    stage('🧪 Parallel Testing') {
      parallel {
        stage('Unit Tests') {
          steps {
            sh 'mvn test -Dtest="*Unit*" --batch-mode'
          }
          post {
            always {
              junit 'target/surefire-reports/*Unit*.xml'
            }
          }
        }
        stage('Integration Tests') {
          steps {
            sh '''
              mvn verify \
                -Dtest="*Integration*" \
                -Dspring.profiles.active=test \
                --batch-mode
            '''
          }
          post {
            always {
              junit 'target/failsafe-reports/*.xml'
            }
          }
        }
        stage('Code Coverage') {
          steps {
            sh '''
              mvn test jacoco:report --batch-mode
              awk '/Total/{print "Coverage: " $NF}' target/site/jacoco/index.html
            '''
          }
          post {
            success {
              publishHTML([
                reportDir: 'target/site/jacoco',
                reportFiles: 'index.html',
                reportName: 'JaCoCo Coverage'
              ])
            }
          }
        }
      }
    }

    stage('📊 Code Quality Gate') {
      when { not { expression { params.FORCE_DEPLOY_PROD } } }
      steps {
        withSonarQubeEnv('SonarQube') {
          sh """
            mvn sonar:sonar \
              -Dsonar.projectKey=${SONAR_PROJECT} \
              -Dsonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml \
              --batch-mode
          """
        }
        timeout(time: 5, unit: 'MINUTES') {
          waitForQualityGate abortPipeline: true
        }
      }
    }

    stage('🐳 Docker Build & Scan') {
      steps {
        script {
          withAWS(credentials: 'aws-ecr-credentials', region: AWS_REGION) {
            sh 'aws ecr get-login-password --region ${AWS_REGION} | docker login --username AWS --password-stdin ${DOCKER_REGISTRY}'
          }

          sh "docker build -t ${env.FULL_IMAGE} --build-arg VERSION=${env.IMAGE_TAG} ."

          // Security Scan
          sh """
            trivy image \
              --exit-code 0 \
              --severity HIGH,CRITICAL \
              --format table \
              --output trivy-report.txt \
              ${env.FULL_IMAGE}
            cat trivy-report.txt
          """

          // Push karo
          sh """
            docker push ${env.FULL_IMAGE}
            docker tag ${env.FULL_IMAGE} ${DOCKER_IMAGE}:latest
            docker push ${DOCKER_IMAGE}:latest
          """

          archiveArtifacts 'trivy-report.txt'
        }
      }
    }

    stage('🚀 Deploy Staging') {
      when {
        anyOf {
          branch 'develop'
          branch 'release/*'
        }
      }
      steps {
        script {
          deployToK8s(
            namespace:   "${K8S_NAMESPACE}-staging",
            service:     SERVICE_NAME,
            imageTag:    env.IMAGE_TAG,
            kubeConfig:  'k8s-staging-config',
            strategy:    'RollingUpdate'
          )

          // Smoke tests
          sh """
            sleep 30
            for i in 1 2 3 4 5; do
              STATUS=\$(curl -sf https://staging-api.company.com/${SERVICE_NAME}/actuator/health | python3 -c "import sys,json; print(json.load(sys.stdin)['status'])" 2>/dev/null)
              if [ "\$STATUS" = "UP" ]; then
                echo "✅ Smoke test passed after \$i attempts!"
                exit 0
              fi
              echo "Attempt \$i: Service not ready, waiting..."
              sleep 10
            done
            echo "❌ Smoke test FAILED!"
            exit 1
          """
        }
      }
    }

    stage('✅ Production Approval') {
      when {
        allOf {
          branch 'main'
          not { expression { params.FORCE_DEPLOY_PROD } }
        }
      }
      steps {
        script {
          sendSlackNotification(
            channel: '#deployments',
            message: "🔔 *Production Deploy Pending Approval*\nService: `${SERVICE_NAME}:${env.IMAGE_TAG}`\n<${env.BUILD_URL}input|Click to Approve or Reject>"
          )

          def approver = input(
            message: "Deploy ${SERVICE_NAME}:${env.IMAGE_TAG} to PRODUCTION?",
            ok: 'Deploy to Production',
            submitter: 'tech-lead,devops-team',
            submitterParameter: 'APPROVED_BY'
          )
          echo "Approved by: ${approver}"
          env.APPROVER = approver
        }
      }
    }

    stage('🌍 Deploy Production') {
      when {
        anyOf {
          branch 'main'
          expression { params.FORCE_DEPLOY_PROD }
        }
      }
      steps {
        script {
          deployToK8s(
            namespace:  K8S_NAMESPACE,
            service:    SERVICE_NAME,
            imageTag:   env.IMAGE_TAG,
            kubeConfig: 'k8s-prod-config',
            strategy:   'BlueGreen'
          )

          // Post-deploy verification
          sh """
            echo "Verifying deployment..."
            kubectl rollout status deployment/${SERVICE_NAME} \
              -n ${K8S_NAMESPACE} \
              --timeout=5m
            
            kubectl get pods -n ${K8S_NAMESPACE} \
              -l app=${SERVICE_NAME} \
              --no-headers | awk '{print "Pod: " \$1 " Status: " \$3}'
          """
        }
      }
    }
  }

  post {
    always {
      script {
        // Metrics publish (Prometheus/Grafana ke liye)
        def duration = currentBuild.duration
        def result   = currentBuild.currentResult

        sh """
          curl -s -X POST http://metrics-collector:9091/metrics/job/jenkins_build \
            -H "Content-Type: text/plain" \
            -d 'jenkins_build_duration_ms{job="${SERVICE_NAME}",branch="${env.BRANCH_NAME}",result="${result}"} ${duration}'
        """ || true

        // Docker cleanup
        sh "docker rmi ${env.FULL_IMAGE} || true"

        // Workspace cleanup
        cleanWs()
      }
    }

    success {
      script {
        sendSlackNotification(
          channel: '#deployments',
          status:  'SUCCESS',
          message: "Deployed `${SERVICE_NAME}:${env.IMAGE_TAG}` to ${env.IS_RELEASE ? 'PRODUCTION 🚀' : 'STAGING 🔧'}"
        )

        if (env.IS_RELEASE) {
          // JIRA ticket auto-close
          jiraComment(
            site: 'company-jira',
            issueKey: "EC-${env.BUILD_NUMBER}",
            body: "✅ Successfully deployed to production. Version: ${env.IMAGE_TAG}"
          )
        }
      }
    }

    failure {
      script {
        sendSlackNotification(
          channel: '#deployments',
          status:  'FAILURE',
          message: "Build FAILED for `${SERVICE_NAME}`. Check: ${env.BUILD_URL}"
        )

        emailext(
          subject: "❌ BUILD FAILED: ${SERVICE_NAME} #${env.BUILD_NUMBER}",
          body: """
Build failed for ${SERVICE_NAME} on branch ${env.BRANCH_NAME}.

          """,
          to: 'dev-team@company.com,devops@company.com'
        )
      }
    }
  }

Final Interview Preparation – Top 20 Questions

💼 Must-Know Jenkins Interview Questions

Q1: Jenkins kya hai aur kyun use karte hain? Jenkins ek open-source automation server hai jo CI/CD pipelines ko automate karta hai. Code commit se production deployment tak ka poora process automate hota hai – build, test, security scan, deploy. Manual steps eliminate hote hain, speed badhti hai, errors kam hote hain.
Q2: Declarative vs Scripted Pipeline – kab kaunsa use karo? Declarative: Standard choice, readable, validation built-in, shared libraries ke saath best. Scripted: Jab complex Groovy logic chahiye jo Declarative mein possible nahi. Modern teams: Declarative pipeline with script{} blocks for complex logic.
Q3: Jenkins pipeline fail ho gayi – troubleshoot kaise karo? (1) Build logs padho – error message dhundho (2) Stage level mein kahan fail hua (3) Agent pe workspace dekho (4) Environment variables verify karo (5) Credentials expiry check karo (6) Network connectivity test karo (7) Replay feature se debug karo.
Q4: Jenkins High Availability kaise achieve karte hain? Active-passive: JENKINS_HOME shared NFS/EBS pe, secondary controller ready. Active-active: Kubernetes pe Jenkins, multiple replicas (experimental). Best: Jenkins on K8s with PVC for data persistence. RPO < 1 hour, RTO < 15 min achievable.
Q5: Credentials Jenkins mein securely kaise manage karte hain? (1) Jenkins Credential Store – encrypted at rest with master.key (2) HashiCorp Vault integration for enterprise (3) AWS Secrets Manager / GCP Secret Manager (4) Never in code or environment plaintext (5) Rotation strategy (6) Least privilege principle.
Q6: Pipeline speed kaise improve karte hain? (1) Parallel stages for independent tasks (2) Docker layer caching (3) Maven/npm dependency caching (4) Incremental builds where possible (5) Artifact caching between stages (6) Faster agents (SSD, more RAM) (7) Optimize test suites (slow tests identify karo).
Q7: Shared Library ke benefits kya hain? DRY principle – code reuse. Single place maintenance. Version controlled. Team-wide standards enforce. Easier testing of pipeline code. Faster onboarding for new services.
Q8: Jenkins agent kaise add karte hain aur kab add karte hain? Add karte hain jab: Controller load high ho, specialized build environment chahiye (Windows, Android, GPU), parallel builds badhani ho. SSH ya JNLP method. Labels se pipeline mein specific agent target karo.
Q9: Pipeline mein rollback kaise implement karte hain? Docker tags: Previous image tag use karo. K8s: kubectl rollout undo. Blue-Green: Traffic switch back to old color. Database migrations: Reversible migrations, snapshot restore. Canary: Traffic weight revert. Speed of rollback = critical metric.
Q10: Jenkins on Kubernetes ke advantages? Auto-scaling agents (0-infinity), ephemeral builds (fresh environment always), declarative infrastructure, Helm charts se easy deploy, cost efficient with spot instances, no agent maintenance, cloud-native approach.
Q11: Pipeline as Code kyun zaroori hai? Version history: kab kya change hua track karo. Code review: Pipeline changes bhi PR se jaayein. Reproducibility: Naye server pe same pipeline. Disaster recovery: Git se restore karo. Collaboration: Team pipeline improve kar sake.
Q12: Jenkins Plugin kya hota hai aur kaise manage karte hain? Plugin Jenkins functionality extend karta hai. Management: Manage Jenkins → Plugin Manager. Production: Auto-update disable karo – test environment mein test karo pehle, phir production. JCasC se plugin versions pin karo.
Q13: Build kab fail karna chahiye aur kab unstable? FAILURE: Compile error, critical test fail, deployment fail. UNSTABLE: Non-critical test fail, low coverage (warning not blocker). SUCCESS: Sab pass. Unstable code merge block karo, sirf failure se.
Q14: Webhook aur polling mein se kaunsa prefer karo aur kyun? Webhook prefer karo: instant trigger, no polling overhead, exact event-based. Polling fallback (pollSCM) use karo jab Jenkins private network mein ho. Best practice: both configure karo redundancy ke liye.
Q15: Security scan pipeline mein kaise include karte hain? SAST: SonarQube, Checkmarx. Dependency scan: OWASP Dependency Check. Container scan: Trivy, Snyk, Clair. Secrets scan: truffleHog, detect-secrets. API security: OWASP ZAP. DAST staging pe. Fail pipeline on HIGH/CRITICAL findings.
